# Release verification

Every release is built by GitHub Actions from a tag, never on a
maintainer's machine, and ships with the material needed to prove it:
checksums, Sigstore signatures, GitHub artifact attestations, SBOMs, and
the hash of the drop page. This page shows how to check each one. Nothing
here requires trusting the maintainer's laptop.

Replace `vX.Y.Z` with the release you are checking.

## 1. Binaries

Download the archive for your platform and `checksums.txt`,
`checksums.txt.sig`, and `checksums.txt.pem` from the release page.

Checksums:

```bash
sha256sum --ignore-missing -c checksums.txt
```

Signature on the checksums file (keyless Sigstore, tied to the workflow
that built it):

```bash
cosign verify-blob \
  --certificate checksums.txt.pem \
  --signature checksums.txt.sig \
  --certificate-identity-regexp '^https://github.com/xyluxx/burndrop/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  checksums.txt
```

Build provenance (SLSA), checked against GitHub's attestation store:

```bash
gh attestation verify burndrop_vX.Y.Z_linux_amd64.tar.gz --repo xyluxx/burndrop
```

The archive contains `burndrop` (or `burndrop-relay`), the license, and
the SBOM for that build. The binaries print their version:

```bash
burndrop version
burndrop-relay version
```

## 2. Container image

```bash
cosign verify ghcr.io/xyluxx/burndrop-relay:vX.Y.Z \
  --certificate-identity-regexp '^https://github.com/xyluxx/burndrop/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

gh attestation verify oci://ghcr.io/xyluxx/burndrop-relay:vX.Y.Z --repo xyluxx/burndrop
```

Pin images by digest in production; `cosign verify` prints it.

## 3. The drop page

The release notes list the SHA-256 of `page.html` for that version. The
same hash is in `page.sha256` on the release page and inside every
`burndrop` binary of the release. To check a hosted relay:

```bash
burndrop verify-page -relay https://drop.example.com -expect <hash from the release notes>
```

It compares three things: the page the relay actually serves, the hash the
relay reports about itself, and the hash embedded in your binary. Any
difference is printed and the command fails.

By hand:

```bash
curl -s https://drop.example.com/drop | sha256sum
sha256sum -c page.sha256    # against the downloaded page.html
```

The browser extension does the same check from the browser (verify mode)
and, for relays you add to it, never loads the hosted page at all.

Reproducing the page: `cd web && npm ci && node build.mjs --version vX.Y.Z`
produces `dist/page.html` with the same hash as the release, because the
build inlines pinned dependencies and no timestamps.

## 4. SBOMs

Each archive carries an SPDX SBOM (`*.sbom.json`) generated by Syft.
Scan it with your tool of choice, for example:

```bash
grype sbom:burndrop_vX.Y.Z_linux_amd64.sbom.json
```

## 5. npm and PyPI packages

`@burndrop/sdk` on npm is published with provenance through npm trusted
publishing:

```bash
npm audit signatures
```

`burndrop` on PyPI is published with PEP 740 attestations through PyPI
trusted publishing; the file's page on PyPI shows the verified provenance
(the repository and the workflow that produced it).

## 6. Browser extension

The release includes `burndrop-extension-chrome.zip`,
`burndrop-extension-firefox.zip`, and a `.sha256` file for each. Check
the hash before loading an unpacked extension; the packaged file lists
the same hash in its `page.meta.json`.

## What a match proves, and what it does not

A verified binary or image proves that GitHub built it from the tagged
commit with the workflow in the repository. A verified page hash proves
that a relay serves the page that was released. Neither proves that the
code is correct; that is what `docs/threat-model.md`, the test suites, and
independent review are for.
