## Decisions taken without you

All of them are revertable. The full list with reasoning is in `docs/design.md` section 18 and in `PROGRESS.md`.

1. **Name: burndrop.** Free on npm, PyPI, GitHub, and as .dev and .io at the time of checking (`docs/research/naming.md`). A rename is a global replace of `burndrop`, `BURNDROP`, `Burndrop` plus the banner SVGs.
2. **License: Apache-2.0** (`docs/design.md` section 17).
3. **Module path `github.com/burndrop/burndrop`**, an organisation named after the project. If you prefer your own account, replace the path everywhere (`go.mod`, imports, workflows, README badges, `docs/release-verification.md` identity regexp, `deploy/compose` image name).
4. **SDKs return values to the calling program** instead of carrying the storage manager. The design's section 9 wanted native storage backends in the SDKs; the Go binary has them, and the SDKs document that values must go to `run_with_secret` or the program's own store, never to a model. This kept both SDKs at one runtime dependency each and fully interoperable with the Go implementation.
5. **Reveal AAD carries name and keeps_copy but not the drop ID** (the relay assigns the ID after the ciphertext exists; the per-reveal random key already prevents swaps).
6. **`send_secret` has `delete_after` instead of a note field**; reveal envelopes carry no metadata by spec.
7. **Only secrets marked sendable can be sent back**: captured command output is sendable, values received from humans are not unless the request said so.
8. **Storage ranking**: password managers above the OS keychain, cloud and team managers below it, so a laptop with an AWS login is not told to keep personal secrets in a cloud account.
9. **Relays without agent auth meter anonymous agents per client address**, and CORS admits `chrome-extension://` and `moz-extension://` origins so the extension's bundled page can call the API.
10. **Page hash is hex SHA-256 everywhere** (build output, relay info, CLI, release notes).
11. **Two-step reveal confirmation is not implemented**; it is on the roadmap as an option for organisations whose link scanners click buttons. The current design already requires a click and never burns on GET.

## Known gaps and small warts

- A sent reveal cannot be revoked from the CLI or MCP after `send_secret` returns; the relay supports it, the agent does not expose it. Roadmap.
- `Agent.LoadRedactions` and the `import` record source exist without callers; harmless.
- The saved config writes `max_output_bytes = 0` under `[run_with_secret]` because the TOML encoder cannot omit an empty table; 0 means the default.
- `/api/v1/info` field names, the ciphertext limit (65,840 bytes), and the rate limit burst (rate divided by three, plus one) differ slightly from the numbers in `docs/design.md`; the reference docs describe the code.
- `burndrop verify-page` checks the page the relay serves; in a split deployment (page on a static host) compare the static copy with `sha256sum` instead.
- The extension's Firefox add-on ID is a placeholder (`burndrop-extension@burndrop.example`) that must be replaced before the first Mozilla submission and can never change afterwards.
- Store listings for the extension, a PyPI wrapper for the CLI, and translations are roadmap items in the README.

## Steps to go public

1. Review this file, `PROGRESS.md`, and `docs/design.md` sections 18 and 19. Decide the name, the license, and the module path.
2. Confirm nothing personal is in the tree: `git log --format='%an <%ae>'` shows one identity; the hygiene greps in `Makefile` (target `hygiene`) and `.github/workflows/hygiene.yml` are clean.
3. Create the GitHub repository (an organisation `burndrop`, or your account with the module path replaced). Start private if you want CI to run before anyone sees it. Push `main`.
4. Repository settings:
   - Branch protection on `main` with required checks `ci`, `codeql`, `hygiene`, and code owner review (`.github/CODEOWNERS` names `@Ziadtalha`).
   - Actions: allow the pinned actions; workflows use `id-token: write` for Sigstore and attestations and `packages: write` for ghcr.io. No secrets are needed for the GitHub release or the container image.
   - Enable Dependabot alerts and security updates (`.github/dependabot.yml` is in place), private vulnerability reporting (`SECURITY.md` points to it), and OpenSSF Scorecard (public repositories only).
5. Package registries, before the first tag:
   - npm: create the organisation `@burndrop` (for `@burndrop/sdk` and the `@burndrop/cli-<os>-<cpu>` platform packages) and reserve the unscoped name `burndrop`. Configure trusted publishing for this repository and the `release.yml` workflow on each package; the workflow publishes with `--provenance` and no token.
   - PyPI: reserve `burndrop` and configure a trusted publisher for the repository, workflow `release.yml`, environment `pypi`. Create the `pypi` environment in the repository settings.
6. Tag `v0.1.0` and push the tag. The release workflow builds the page, the extension, the binaries, the image, publishes the packages, verifies its own artifacts, and turns the draft release into a published one with the page hash and image digest in the notes. Follow `docs/release-verification.md` from a clean machine.
7. After the push, check the contributors graph and `git log` on GitHub: only your identity should appear.
8. Badges in the README activate as the workflows run for the first time; the Go Report Card and pkg.go.dev entries appear after their first crawl.
9. Optional: submit the extension to the Chrome Web Store and Mozilla Add-ons (replace the placeholder ID first), and add the demo GIF to the release announcement.
