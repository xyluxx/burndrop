# Contributing

Thank you for looking at burndrop. Contributions of every size are welcome:
bug reports, documentation fixes, new storage backends, translations of the
drop page copy, and security review most of all.

## Before you start

- Read `docs/design.md` (the specification) and `docs/threat-model.md`.
  Changes that weaken a documented property will not be merged, however
  convenient they are.
- Open an issue before a large change so the approach can be agreed first.
- Security findings go through `SECURITY.md`, not issues.

## Development setup

Requirements: Go (the version in `go.mod`), Node 22 or later, and for the
Python SDK, `uv`. Docker is optional (Redis store tests, container image).

```bash
git clone https://github.com/burndrop/burndrop.git
cd burndrop
make test          # Go unit tests (make race adds the race detector and coverage)
make web           # builds web/dist/page.html and runs the page's unit tests
make e2e           # Playwright against a real relay (needs: cd web && npx playwright install chromium)
make hygiene       # em dash, attribution, pinned actions, generated files (CI adds a gitleaks scan)
```

`make help` lists every target. The Go relay embeds `web/dist/page.html`;
run `make web` before `go build ./cmd/burndrop-relay` if you want the page in
your local binary.

## Rules that CI enforces

1. No em dash character (U+2014) anywhere: code, comments, docs, UI text,
   commit messages. Use a comma, a colon, or a new sentence.
2. No AI attribution: no `Co-Authored-By` trailers naming an AI, no
   "Generated with" or "Generated by" lines. Commits carry the author's own
   identity.
3. Conventional commit messages: `feat(scope): ...`, `fix(scope): ...`,
   `docs: ...`, `test: ...`, `chore: ...`, `ci: ...`, `refactor: ...`.
4. No secrets, personal data, real client names, or internal URLs in the
   tree or the history. Use `relay.example` and `drop.example.com`.
5. GitHub Actions pinned by commit SHA. Dependencies pinned to exact versions.
6. `gofmt`, `go vet`, and the TypeScript type check pass; tests pass with
   `-race`; statement coverage stays above the floor in `ci.yml` (80 percent).

## What a good pull request looks like

- One change per pull request, with a description that says what changed
  and why, and how you tested it.
- Tests for behavior, including the failure path. A storage backend needs
  the conformance suite (`internal/storage/suite_test.go`) plus a faithful
  fake of the vendor CLI, and a page under `docs/backends/`.
- Anything that touches `internal/crypto`, `web/src/crypto.ts`, or the SDK
  crypto modules must keep `spec/vectors.json` passing in every language.
  If the vectors need to change, explain why in the pull request and update
  `docs/crypto-spec.md`.
- No new dependency without a sentence on why it is needed and what it
  replaces.
- Documentation updated in the same pull request.

## Adding a storage backend

1. Implement `storage.Backend` in `internal/storage/<name>.go`. Values must
   never appear in command arguments, environment variables of child
   processes, or log lines. Use `Runner` for vendor CLIs.
2. Add a fake runner and run the conformance suite against it.
3. Add the config struct and the `OpenBackend` case in
   `internal/agent/config.go`, and the name in `KnownBackends`.
4. Document it in `docs/backends/<name>.md` and add a row to
   `docs/storage-backends.md`.
